# 邮件分析流程

质量验证使用独立的[邮件分析回放评测](mail-evaluation.md)，可运行合成脱敏案例、比较 Skill 候选并生成规则检查与人工复核报告。

邮件摘要与交互聊天共用 `internal/agentruntime` 的结构化工具执行循环、调用 ID 配对、上下文预算和结束校验。后台摘要从当前用户的 Skill 管理配置中读取流程；`mailstore/skills/mail-analysis/SKILL.md` 是首次初始化时复制的默认内容，之后的编辑和删除不会被启动流程覆盖。不创建额外的智能体记录或聊天会话。现有邮箱绑定的智能体提示词作为业务偏好，模型选择继续生效；邮件总结不再按输出标签分栏。

## 输入与检索

- 最新触发邮件直接提供给模型，包括正文、引用/转发、签名和附件元数据。引用只分区，不提前删除。回复建议也保留完整正文；翻译继续沿用自己的引用处理规则。
- 默认优先搜索明确的 RFC 回复链，然后搜索同一参与人的往来邮件，必要时搜索当前邮箱。相同参与人不代表相同订单，skill 要求核对型号、订单号、报价号等关联信息。
- 数据访问只开放 `search_emails` 和 `read_email`，另注册用于最终交付的 `submit_result`。邮箱身份由服务端注入，工具参数不能切换账号。搜索和读取均限制到触发邮件时间，同一文件夹还限制到触发邮件 UID。
- 会话候选只加载最多 200 条近期邮件头，显式引用的旧邮件另外加载；范围可能不完整时返回 `scopeLimited`，可用邮箱检索继续定位。所有检索覆盖的都是已同步数据；尚未同步的历史内容不代表不存在。
- 搜索结果用于定位，历史事实需读取原文。初始完整正文最多提供 16,000 个 Unicode 字符，超出后通过字符偏移分段读取；若最终未读完触发邮件，分析失败。附件仅提供元数据，不读取附件内容。

## 输出与缓存

模型通过原生 `submit_result` 提交 `request`、`background`、`changes`、`actions`、`missing` 和 `summary`。服务端校验内部分析结构及摘要长度；正文中的 `[folder/uid]` 标注只是说明性引用，不参与校验，真实的证据记录由服务端从实际工具调用生成：来源、正文读取范围、工具活动和 skill 版本与短摘要在同一个更新中写入 `message_summaries.analysis_json`。

界面和飞书直接展示 `summary` 自由文本，不要求客户、需求、要求、问题等固定栏目，全文最多 200 个 Unicode 字符（含标点）。超长输出会反馈模型压缩重写，不再逐字段机械截断；若在预算内仍不合格则报告失败。`POST /api/ai/mail-summary` 的顶层 `summary` 与 `analysis.summary` 相同。旧结果继续可读，重新总结后采用新格式；历史 `analysis.fields` 仅用于兼容读取。

每次分析最多 6 轮工具交互、12 次工具调用，单次返回最多 4 个调用，总执行时间上限 90 秒。模型仍受原有供应商客户端的单次请求超时限制。

缓存指纹包含 skill 内容、模型配置、智能体提示词和标签，以及实际读取的来源内容。来源改变或删除会使结果标记为过期；旧结果保持可读，只有显式重新总结才重新生成。旧数据库通过新增 `analysis_json` 列升级，不改写旧摘要。

流水线 v8 另外记录 `retrieval` 检索依赖清单：初始相关邮件范围的邮件头指纹、实际执行过的查询及其完整匹配集合指纹。候选展示仍有分页和 200 条范围限制，但指纹以流式方式扫描匹配邮件头，能够发现没有进入已展示页的迟到旧邮件。缓存检查重用搜索的账号、时间、UID 和过滤条件；更晚邮件、其他邮箱和已读标记变化不会使旧结果过期。这里的“完整”仅指本地已同步匹配集合，不能代表远端历史已同步完整或全部正文已读；正文覆盖仍以 `sources.ranges` 和 `missing` 为准。匹配集合很大时，缓存检查成本随匹配邮件数增加。

流水线 v9 的公共工具解析器兼容多个连续的完整 JSON 工具对象（缺少代码围栏或外层数组），仍要求整段都是合法工具调用；混入最终结果或残缺对象时不执行有效前缀。这修复了真实回放中模型请求工具却被误当成最终输出的问题。

流水线 v11 将聊天与后台总结切换到同一个原生工具执行器。工具调用与工具结果使用供应商的结构化协议及调用 ID，推理续传数据只在当前执行内存中保留。邮件总结入口注册输出 schema，校验失败在原有轮数和上下文预算内最多修正两次；最终结果引用仍须对应实际读取的邮件。旧的 JSON/DSML 文本解析只保留给兼容适配和历史内容清理，生产工具调用不再从文本中推断。架构分层与协议边界见 [Agent 执行内核](agent-runtime.md)。

流水线 v12 将展示摘要改为 200 字以内的自由文本，移除邮件总结的输出标签约束。默认 Skill 同步更新；已保存的 Skill 保留用户内容，执行入口的输出约定会明确覆盖旧流程中的分栏要求。旧缓存会显示为待更新，重新生成后才使用新摘要。

流水线 v13 采用通用 Agent 的输出约定：最终回答即交付物，服务端只校验结构（JSON 键与摘要长度），不再校验回答文本中的邮件引用。此前"引用了未读取邮件即整次分析失败"的防线被移除——模型引用预览、写错 UID 或把日期写成 `[2026/10/25]` 都不会让任务失败；证据完整性改由结构保证：`sources` 与 `activity` 始终来自实际 `read_email` 调用，触发邮件头信息始终完整提供，正文不可用或部分读取等确定性缺口由服务端写入 `missing`。读取纪律（历史事实须 read_email 核对、只标注已读邮件）保留在 Skill 与执行约定的指令层，由评测套件离线度量而非运行时强制。触发邮件正文超出 16,000 字符且未读完时仍拒绝保存，因为截断输入上的业务摘要会误导决策。默认 Skill 同步更新；旧缓存显示为待更新。

分析结束前重新检查检索依赖和已读取的历史正文；运行期间发生变化时拒绝保存混合版本的分析并允许任务重试。流水线升级保留旧总结，旧版结果显示为待更新。

## Skill 加载与管理

交互聊天的自动模式只注入有独立大小预算的 Skill 目录。模型通过 `load_skill` 按需读取完整流程和依赖，工具按 Unicode 字符分段，单段最多 2000 字；明确选择的 Skill 则直接加载。依赖代表指令组合，不是服务器强制执行的步骤图。账号范围、品牌权限、工具实现和输出协议始终由服务器控制。

每次执行冻结当前用户的目录和 Skill 内容，中途通过 API 更新只影响后续执行。聊天响应及其持久化结果中的 `skillSnapshots` 记录请求加载的版本；邮件分析的 `skillSnapshot` 保留根流程、完整依赖版本和内容指纹。分页读取某个 Skill 不代表它已全部读完。

Skill 管理只保存当前内容，提供新增、编辑、启停、删除和邮件总结流程选择，支持页面与 API Key。保存后供后续执行使用，不保留历史版本或提供恢复接口。`revision` 仅用于并发编辑校验，页面不显示版本号。升级时移除旧的历史归档表，保留当前 Skill、依赖关系和已有执行快照。

设计参考：DeepSeek Harness 的 [Skill 目录与加载器分离](https://github.com/deepseek-ai/deepseek-harness/tree/master/packages/skill/tool-skill)，以及 Codex 的 [Skill 实际访问识别](https://github.com/openai/codex/blob/main/codex-rs/skills/src/invocation.rs)。本项目在现有 Go 执行内核和数据库上实现，并记录执行快照及邮件检索依赖，没有引入这些仓库的运行时依赖。

## 通知

增量同步将新邮件和 `mail_tasks` 中的分析、回复建议、通知任务在同一事务中保存，初始历史同步不创建任务。分析和回复建议沿用各自的邮箱任务开关，未配置或已禁用的任务会跳过；通知只在新邮件首次入队时飞书已启用的情况下创建，后来开启通知不会补发旧邮件。

后台调度由 `mailTaskRunner` 管理，IMAP 适配层只提供同步就绪条件和任务执行。每个邮箱拥有独立的 AI 通道与通知通道；每个通道最多执行一个任务，数据库原子领取保证多进程也遵守限制。后台分析与回复建议共享最多 4 个全局执行名额，分析优先于回复建议；该上限不包含交互聊天或手动分析。通知使用自己的通道，不占 AI 名额，也不等待 IMAP 全量刷新。AI 任务仍在收件和发件刷新完成后启动。

通知等待本封邮件的第一次分析完成；摘要就绪、第一次分析失败或跳过后即可执行。等待超过入队时间 30 秒时，也可领取基础通知。该规则不依赖其他邮件或回复建议的完成。调度每 5 秒检查或在任务完成时唤醒；30 秒是等待摘要的门槛，实际投递还取决于通知队列及网络。已冻结的投递重试不再等待分析。

任务租约为 3 分钟，重启后恢复过期租约。AI 单任务上限 100 秒、分析内部上限 90 秒，通知上限 15 秒。临时失败从 15 秒开始指数退避并加入约 ±20% 抖动，退避上限 30 分钟；服务端 `Retry-After` 可延长等待（最多 24 小时）。分析最多尝试 5 次，回复建议 3 次，通知 8 次。401/403、其他不可重试 4xx 和明确的配置错误直接进入失败状态；结构化输出校验失败最多尝试两次。账户停止或进程正常退出导致的取消记录为 interrupted，不消耗失败次数。超时仍计为一次失败。

正文不可用或首次分析失败时，通知任务发送包含发件人和主题的基础收件通知；成功则发送配置格式的摘要。通知内容在第一次发送前冻结，投递失败独立重试，不重复调用模型。发送成功后不会因同步重放或后来分析成功而另发一条通知。若远端已接受请求但本地未收到响应，网络重试仍可能产生重复投递。

飞书必须返回有效的成功确认；HTTP 200 的空响应或 HTML 页面不能被当作发送成功。网络错误不记录带令牌的请求 URL。投递仍采用至少一次语义，远端已接受但响应丢失时可能重复。

`GET /api/settings/ai/mail-tasks?accountEmail=...&folder=INBOX&messageId=...` 查询当前用户邮箱的任务状态。`POST /api/settings/ai/mail-tasks/retry` 接受 `accountEmail`、`folder`、`messageId`、`taskType`（`analysis` / `reply` / `notification`），允许显式重试终止的失败任务（包括修复配置后重试），不能重放已成功的通知。

## 后台执行记录

`mail_task_runs` 与任务领取、完成和失败在同一事务内写入。每次尝试有独立的 `mail_run_*` 标识，与内部租约令牌不同；记录执行阶段、开始/结束时间、耗时、错误分类、是否可重试，以及实际生成时的模型、配置指纹和 Skill 依赖版本。命中已有缓存时记录缓存和过期状态，版本信息来自被复用的结果。失败不覆盖前一次记录，租约被恢复时旧记录标记为 expired。每封邮件的每种任务保留最近 50 次尝试；删除邮件会级联清理相关记录。旧任务在升级后的下一次领取时开始记录历史，不虚构升级前的尝试。

`GET /api/settings/ai/mail-tasks/runs?accountEmail=...&folder=INBOX&messageId=...&taskType=analysis&limit=50` 查询当前用户的运行记录。只返回诊断元数据，不返回通知内容、邮件正文、租约令牌或密钥字段。此接口支持现有 API Key 身份验证；当前没有单独的运行记录管理页面。
