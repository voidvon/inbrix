Your mail, calendar and contacts — on your own terms.

lilmail is a self-hostable PIM client that talks to your own IMAP/SMTP, CalDAV and CardDAV account and ships as one Go binary. Server-rendered HTML, every asset embedded — no build step, no CDN, no database to provision, and no service in the middle. Drop it next to a config.toml and it runs on 64 MB of RAM.

What's in the binary

Everything a mail client needs. Nothing it doesn't.

Core mail is always on. Calendar, contacts, real-time notifications, AI and multi-account are opt-in config sections that add zero overhead while disabled.

One binary, no database

Templates and vendored JS are compiled in with embed.FS; durable state lives in an embedded bbolt file. An optional Postgres backend is there for shared or multi-instance deploys. Runs air-gapped with only a config.toml.

Mail that just works

IMAP browsing and SMTP sending, JWZ conversation threading, plain-text and rich-text compose, attachments with inline cid: images, scheduled send, and drafts that auto-save every 30 seconds.

Stable /v1 JSON API

Folders, paginated messages, search, flags, move/archive/spam, snooze, compose and drafts, attachments, calendar, contacts and settings — served by the same engine and the same session auth as the HTMX UI.

OAuth2 / OpenID Connect

Authorization-code flow with PKCE (S256), automatic refresh-token handling and XOAUTH2 / OAUTHBEARER SASL. Sign in with your identity provider — classic password login keeps working alongside it.

Calendar & contacts

CalDAV month and week views with event CRUD, free/busy and end-to-end iTIP/iMIP meeting invites. CardDAV address-book lookup powers recipient autocomplete.

opt-in · [caldav] / [carddav]

Real-time & AI, opt-in

An IMAP IDLE watcher, SSE stream, browser notifications and VAPID Web Push — plus smart compose, thread summaries and phishing detection through any OpenAI-compatible endpoint you point it at.

opt-in · [notifications] / [ai]
The shape of it

No one in the middle. Not even us.

lilmail is a client, not a service. It runs on your machine and speaks straight to the mail server you already have — there is no lilmail account, no relay, and nothing phoning home.

You Your browser

Server-rendered HTML over HTMX — or any client on /v1.

Your server lilmail

One Go binary + config.toml. bbolt on disk, or your Postgres.

Your accounts IMAP · SMTP · DAV

Gmail, Outlook, or any standards-compliant server, over OAuth or password.

a lilmail relay — does not exist. There is no hosted lilmail to sign up for.

Screens

Warm, quiet, and quick.

A hand-written design system — no framework, no utility soup — with a real dark mode. Every screen below is a live screenshot, generated by the repo's own Playwright script.

Three-pane inbox. Folders, threaded list and reading pane, with unread dots, attachment markers and per-sender avatars.

Reading a message. HTML mail renders inside a sandboxed iframe; the action row covers reply, forward, archive, flag, print and delete.

Compose. Plain-text or rich-text, attachments with inline cid: images, drafts auto-saved every 30 seconds, and send-later scheduling.

Search. Server-side IMAP search across the current folder, exposed identically at GET /v1/search.

Settings. Signatures, send-as identities, vacation responder, notifications and connected accounts — each one also reachable over /v1/settings.

Sign in. Email plus mail-server password, or a full OAuth2 / OIDC authorization-code flow with PKCE when it's configured.

Quick start

Running in about a minute.

There is no account to create and nothing to provision. Point lilmail at the mailbox you already have and open it in your browser.

~/ — build and run
git clone https://github.com/vul-os/lilmail.git
cd lilmail

# copy the annotated example and fill in your server
cp config.toml.example config.toml

go run main.go        # or: make build && ./lilmail
# → http://localhost:3000
~/lilmail — run the release archive
# download the archive for your OS from the Releases page,
# extract it, and put a config.toml next to the binary
cp config.toml.example config.toml

./lilmail             # → http://localhost:3000
./lilmail -version    # print version and exit
~/lilmail — container
docker build -t vulos/lilmail .

docker run -p 3000:3000 \
  -v $PWD/config.toml:/app/config.toml \
  vulos/lilmail
Generate real secrets before you deploy: openssl rand -hex 32 for jwt.secret, and a random 32-character encryption.key (AES-256) for credentials at rest.
  1. 1
    Get the binary

    Build it with Go 1.23+, pull a release archive, or run the container. Only config.toml has to sit alongside it.

  2. 2
    Point it at your mailbox

    A minimal config is an IMAP server, a JWT secret and a 32-character encryption key. Every optional section is disabled until you add it.

  3. 3
    Sign in

    Open http://localhost:3000 and use your email and mail-server password — or the OAuth2 button once [oauth2] is configured.

config.toml — the minimum
[server]
port = 3000

[imap]
server = "imap.example.com"
port   = 993
tls    = true

[smtp]
port         = 587
use_starttls = true

[jwt]
secret = "change-me-to-a-long-random-string"

[encryption]
key = "a-32-character-encryption-key!!"
The contract

One engine, two front doors.

The HTMX UI and the /v1 JSON API are served by the same mail engine under the same session auth. Build a rich client, a script, or a widget on top — the shapes are treated as a stable, additive contract.

GET/v1/folders
GET/v1/messages?folder=INBOX&limit=50
GET/v1/messages/:uid
GET/v1/search?q=invoice
PATCH/v1/messages/:uid/flags
POST/v1/messages/:uid/move
POST/v1/messages  · send or schedule
POST/v1/attachments
GET/v1/calendar/events
GET/v1/contacts
fetch the first page of the inbox
curl -s --cookie jar.txt \
  'http://localhost:3000/v1/messages?folder=INBOX&limit=25' \
  | jq '.messages[0] | {from, subject, date}'

The API reuses the session cookie from POST /login or the OAuth2 flow — there is no second token scheme to manage. Unauthenticated calls answer 401 with JSON instead of redirecting.

Self-hosted by design

Independent, all the way down.

Think Evolution plus Evolution-Data-Server, for the web: a fully independent project with no hosted service behind it and nothing it needs from anyone else's infrastructure.

Your own accounts

lilmail connects to the mailbox you already own — Gmail, Outlook or any standards-compliant server — over OAuth or password.

  • No lilmail account to create
  • No relay handling your mail
  • Multi-account with per-account error isolation

No external services

Frontend assets are embedded with embed.FS and durable state is a local bbolt file, so an offline box is a supported deployment.

  • No CDN, no asset pipeline
  • No database server to provision
  • Linux, macOS and Windows builds

Security-first

Sensible defaults instead of options you have to remember to turn on, and a threat model written down in the docs.

  • JWT sessions; AES-256-GCM credentials at rest
  • Strict CSP and SameSite=Lax cookies
  • Sandboxed mail iframe; CR/LF/NUL header guards
