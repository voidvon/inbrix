# inbrix 产品库导入闭环

从"调研一个品牌的产品"到"线上产品库带价格可报价"的完整流程。六个阶段:连接 → 调研 → 分类 → 建档(规格文本) → 目录(维度+变体+价格) → 校验。

## 第 0 步:连接与现状

1. 读项目根 `.env` 拿 `API_URL` 和 `API_KEY`,用 `Bearer` 头调用。
2. 用 `scripts/inbrix_api.py` 冒烟(只读):`python3 .agents/skills/inbrix-product-import/scripts/inbrix_api.py whoami && python3 ... list`。确认服务器可达、当前用户、现有产品/分类/维度,避免重复建档。
3. **先读 `references/api.md`**——数据模型、校验规则和 PUT 覆盖语义都在那里。不读就动手必然踩坑(见"红线")。

## 第 1 步:产品资料调研

- 优先官方技术信息表(spiraxsarco.com 的 `*.ashx` 中文 TI PDF,`WebFetch` 不支持 PDF 时用 curl 下载后用 Read 读)。
- **不编造参数**:查不到官方资料的型号(如 43D 减压阀、SV617、M18、PS),不建档,在总结里说明;可用官方现行等价型号替代并注明。
- 每个产品记录:型号、中文名、细分类别、2–4 句概述、参数表(连接/口径/压力/温度/材质/Kv)、典型应用、技术资料编号。

## 第 2 步:分类设计

- 顶级分类用**简单直接的产品类型名**:减压阀、安全阀、控制阀、流量计、球阀、止回阀、截止阀、过滤器、汽水分离器、视镜、凝结水回收、排污阀……
- 只有疏水阀这类按工作原理区分的才建子分类:浮球式/倒吊桶式/热动力/热静力,挂在"疏水阀"下。
- 不建"管道附件""压力与流量控制"这类中间分组层。

## 第 3 步:创建产品(规格文本)

- `POST /api/products`,name(含型号+中文名)/ brand / model / categoryId / specification。
- **specification 只写三节 Markdown**:`## 产品概述`、`## 典型应用`、`## 技术资料`(有价格后再追加 `## 报价说明`)。参数表格一律不进规格文本——参数属于第 4 步的目录结构,别把两套体系混了。
- 价格口径说明写进 `## 报价说明`(价格来源、口径差异、"价格另询"项)。

## 第 4 步:目录结构(维度 + 变体)

- **维度**是 owner 级共享字典,产品保存时内联定义自动并入;同 key 复用字典定义。类型只用 `text`/`number`(number 带单位),**不要用 select**(跨产品保存时不合并选项,极易校验失败)。key 必须 `^[A-Za-z0-9_-]{1,40}$`。
- **每个可购买的规格 = 一个独立变体**。口径绝不能写"DN15~150"这种范围;连接方式/PN 等级/阀座材质/阀体材质/配置(整机 vs 组合单元)都作为变体属性拆分成独立变体。SKU 用 `型号-配置-DNxx` 风格。
- 现有共享维度先查 `GET /api/product-dimensions` 复用(适用介质/连接方式/口径/阀体材质/最高工作压力/最高工作温度/Kv 值/结构形式/密封与阀座/价格年份等已存在)。
- 校验硬限制:每产品 ≤40 维度、≤500 变体;每个变体必须填满全部维度;SKU 与属性组合不得重复。完整规则见 `references/api.md`。

## 第 5 步:价格

- **价格记录只写 `{"amount": "<金额>", "currency": "CNY"}`**。不要 taxRate/taxMode/validFrom/source/minQty——用户明确要求纯金额(带了条件字段前端会弹"旧价格含附加条件"提示,且重填单价会清条件)。
- CSV 价格表匹配规则、口径英寸↔DN 换算、易错点(重名型号陷阱、按材质/连接/PN/阀座拆变体)见 `references/price-csv.md`,匹配前必读。
- **每个有价格的产品加 `price_year`(价格年份,number)维度**,变体值填价格表年份(如 2024)。年度调价就改这个值,报价时靠它识别旧价。只加维度时保留现有变体/价格 ID 原地更新(方法见 api.md)。
- 价格表没覆盖的变体保留但不挂价,在 `## 报价说明` 注明"价格另询"。

## 第 6 步:校验(每阶段都要)

- 分类计数合计 = 产品数;`GET /api/product-navigation` 品牌分组正常。
- 抽查 `GET /api/products/:id`:规格文本、维度、变体、价格逐项核对;用结构化值(如材质字符串)跑 `GET /api/products?q=` 确认全文索引命中。
- 价格覆盖统计:变体数/有价数/带条件字段数(应为 0)。helper 里有现成命令。

## 红线(违反必出事故)

1. **PUT /api/products/:id 用请求体整体覆盖**——省略 `categoryId` 会把产品改成未分类(实际发生过)。每次 PUT 必须带上 name/brand/model/categoryId/specification/version;要保留目录就不传 `catalog`,要改目录就传完整目录。
2. **version 是乐观锁计数器,不是历史版本**(库里永远只有最新一份)。PUT 带 version,遇 409 冲突就重新 GET 拿最新 version 再试;没有历史可回滚,改错只能改回来。
3. 建档/改档脚本放 `tmp/`(已 gitignore),写成幂等(按 name 查重跳过、失败可重跑),方便后续补数据重放。
